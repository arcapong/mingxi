# 랜덤 시크릿(토큰) 및 인코딩

시스템 구축 시 용도별로 안전한 시크릿 키, 토큰, 암호화 키를 생성하는 방법과 인코딩 방식의 차이에 대해 정리한 가이드입니다.

---

## 1. 용도별 시크릿 키 생성 명령어

CLI 환경에서 `openssl` 명령어를 활용하여 강력한 난수를 생성할 수 있습니다. 각 키의 용도와 제약 조건을 확인하여 적절한 명령어를 실행하세요.

| 환경변수명 | 키 용도 | 추천 명령어 | 비고 / 제약 사항 |
| :--- | :--- | :--- | :--- |
| `JWT_SECRET` | HS256 HMAC 서명키 | `openssl rand -base64 48` | 형식 무관 (`auth.ts` 등이 내부적으로 `TextEncoder`를 통해 바이트 변환 처리) |
| `TOKEN_ENCRYPTION_KEY` | AES-256-GCM 대칭 암호화키 | `openssl rand -hex 32` | **★ 반드시 32바이트 Hex(=64자)** 형식 준수 필요 |
| `SYNC_SECRET` | Bearer 인증 토큰 | `openssl rand -hex 32` | 불투명(Opaque) 토큰 형태, 형식 무관 |
| `CRON_SECRET` | Cron 작업 인증 토큰 | `openssl rand -hex 32` | 불투명(Opaque) 토큰 형태, 형식 무관 |

### CLI 명령어 모음

```bash
# 1. JWT 서명용 시크릿 (Base64)
openssl rand -base64 48

# 2. 토큰 암호화키 (Hex 32바이트 = 64자)
openssl rand -hex 32

# 3. 서비스 간 동기화용 Bearer 토큰 (Hex)
openssl rand -hex 32

# 4. 크론 작업 호출 인증용 Bearer 토큰 (Hex)
openssl rand -hex 32
```

## 2. 인코딩 방식의 차이 (Hex vs Base64)

> **핵심:** 선택 기준은 **"그 값이 어디를 오가는가"**입니다. 네트워크로 **전송되는 토큰은 Hex**, 서버에 **머무는 키는 Base64**를 사용합니다. 보안 강도는 인코딩이 아니라 원본 난수의 바이트 수가 결정합니다.

| 구분 | **Hex (Base16)** | **Base64** |
| :--- | :--- | :--- |
| **적합한 용도** | **HTTP 헤더·URL로 전송되는 토큰** (`SYNC_SECRET`, `CRON_SECRET`) | **서버에 머무는 키** (`JWT_SECRET`) |
| **문자 구성** | `0-9`, `a-f`만 사용 → 특수문자가 없어 **이스케이프/파싱 문제 없음** | `+`, `/`, `=` 특수문자가 섞일 수 있음 |
| **표현 효율** | 글자당 4비트 (1바이트 → 2자) | 글자당 6비트 (3바이트 → 4자) → **더 컴팩트** |

### Base64URL

Base64의 문제 문자를 치환한(`+`→`-`, `/`→`_`, 패딩 제거) 변형입니다. 인코딩으로서의 본질적인 차이는 없지만, **URL에 노출될 수 있는 값에는 Base64URL을 쓰는 것이 관행**입니다.

```bash
# Base64URL 형식 토큰 생성
openssl rand -base64 32 | tr '+/' '-_' | tr -d '='
```

## 3. HMAC과 HS256

- **HMAC:** 비밀키를 섞어 해시를 계산하는 **위변조 방지(무결성 검증)** 메커니즘. 키를 모르면 유효한 해시를 만들 수 없으므로, 메시지가 조작되지 않았음을 보장합니다.
- **HS256:** JWT 서명 알고리즘의 한 종류로, **해시함수로 SHA-256을 사용하는 HMAC**입니다. 1번 표의 `JWT_SECRET`이 바로 이 HS256 HMAC의 서명키입니다.

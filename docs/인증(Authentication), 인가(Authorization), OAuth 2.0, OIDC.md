# 인증(Authentication), 인가(Authorization), OAuth 2.0, OIDC

## 1. 개요

인증/인가 관련 용어들은 서로 경쟁하는 같은 선상의 개념이 아닙니다. 개념(무엇을 확인하는가), 프레임워크(어떻게 위임하는가), 프로토콜(무엇으로 신원을 증명하는가)로 구분하면 관계가 명확해집니다.

| 용어 | 구분 | 한 줄 정의 |
| :--- | :--- | :--- |
| **Authentication (인증, AuthN)** | 개념 | "당신은 **누구**인가?"를 확인 |
| **Authorization (인가, AuthZ)** | 개념 | "당신은 **무엇을 할 수 있는가**?"를 확인 |
| **OAuth 2.0** | 프레임워크 | 비밀번호를 넘기지 않고 제3자에게 **권한을 위임(인가)**하는 표준 |
| **OIDC (OpenID Connect)** | 프로토콜 | OAuth 2.0 **위에 얹은 인증 레이어** — "누구인가"를 표준화 |

> **핵심:** OAuth 2.0은 이름과 달리 **인가(Authorization) 프레임워크**입니다. OAuth만으로는 "누구인지"를 표준적으로 알 수 없고, 그 빈자리를 채운 것이 OIDC입니다.

---

## 2. Authentication vs Authorization

| 구분 | **Authentication (인증)** | **Authorization (인가)** |
| :--- | :--- | :--- |
| **질문** | 누구인가? | 무엇을 할 수 있는가? |
| **확인 대상** | 신원 (비밀번호, OTP, 생체정보, ID Token) | 권한 (역할 Role, 정책 Policy, Scope) |
| **순서** | 먼저 수행 | 인증 이후 수행 |
| **실패 시 HTTP 상태** | `401 Unauthorized` | `403 Forbidden` |
| **예시** | 로그인 | 관리자 페이지 접근 제어 |

> **핵심:** `401`은 "당신이 누군지 모르겠다"(사실상 Unauthenticated), `403`은 "누군지는 알겠는데 그럴 권한이 없다"입니다. API 설계 시 두 상태 코드를 이 기준으로 구분해야 합니다.

## 3. OAuth 2.0 — 인가 위임 프레임워크

제3자 앱이 유저의 **비밀번호를 받지 않고도** 리소스에 제한된 범위(Scope)로 접근하도록 권한을 위임하는 표준입니다.

### 3.1 4가지 역할

| 역할 | 정의 | 예시 (캘린더 연동 앱) |
| :--- | :--- | :--- |
| **Resource Owner** | 리소스의 주인 (유저) | 구글 캘린더를 쓰는 나 |
| **Client** | 권한을 위임받는 앱 | 캘린더 연동 서비스 |
| **Authorization Server** | 인증·동의를 처리하고 토큰을 발급 | 구글 OAuth 서버 |
| **Resource Server** | 토큰을 검증하고 리소스를 제공 | 구글 캘린더 API |

### 3.2 주요 Grant (권한 부여 방식)

| Grant | 용도 | 상태 |
| :--- | :--- | :--- |
| **Authorization Code (+ PKCE)** | 유저를 대리하는 앱 (웹/모바일). 유저가 동의 화면을 거쳐 발급 | **표준** — 유저 대상은 사실상 이것 하나 |
| **Client Credentials** | 서버 간(S2S) 통신. 유저 개입 없이 서비스 자격으로 발급 | 표준 |
| **Device Code** | 입력이 제한된 기기 (TV, CLI) | 표준 |
| *Implicit* | *SPA용 축약 플로우* | *폐기 — OAuth 2.1에서 제거, PKCE로 대체* |
| *Resource Owner Password (ROPC)* | *앱이 비밀번호를 직접 수령* | *폐기 — OAuth의 존재 이유를 부정하는 방식* |

### 3.3 토큰 두 가지

- **Access Token:** 리소스 접근용, 수명이 짧음 (분~시간 단위). `Authorization: Bearer` 헤더로 전달.
- **Refresh Token:** Access Token 재발급용, 수명이 김. 클라이언트가 안전하게 보관해야 하며, 유출 시 피해가 크므로 Rotation(1회용 갱신)을 적용하는 추세.

> **핵심:** Access Token은 "무엇을 할 수 있는가"의 증표일 뿐, **"누구인가"의 증명이 아닙니다.** 토큰 문자열 자체에 신원 보장이 없다는 점이 OIDC가 필요한 이유입니다.

## 4. OIDC — OAuth 2.0 위의 인증 레이어

OAuth 2.0의 인가 절차를 그대로 쓰면서, 결과물에 **"누구인지"를 증명하는 ID Token**을 추가한 프로토콜입니다.

| 구분 | **OAuth 2.0** | **OIDC** |
| :--- | :--- | :--- |
| **목적** | 인가 (권한 위임) | 인증 (신원 확인) + 인가 |
| **산출물** | Access Token | Access Token + **ID Token** |
| **유저 정보** | 표준 없음 (제공자마다 다른 API) | **UserInfo 엔드포인트**로 표준화 |
| **요청 방법** | scope에 리소스 권한 나열 | scope에 **`openid`** 포함 (+`profile`, `email`) |
| **설정 정보** | 표준 없음 | **Discovery** (`/.well-known/openid-configuration`) |

### ID Token

- 형식은 **JWT**이며, 발급자(IdP)의 서명을 검증한 뒤 클레임을 신뢰합니다.
- 필수 확인 클레임: `iss`(발급자), `aud`(수신자 = 내 Client ID), `exp`(만료), `sub`(유저 고유 ID), `nonce`(재사용 공격 방지).
- 서명은 보통 **RS256(비대칭)** — IdP의 공개키(JWKS)로 누구나 검증할 수 있습니다. 자사 서비스가 자체 발급하는 세션용 JWT에 흔히 쓰는 HS256(대칭, [랜덤 시크릿(토큰) 및 인코딩](<랜덤 시크릿(토큰) 및 인코딩.md>) 참고)과 달리, 검증 주체가 서명 키를 소유할 필요가 없기 때문입니다.

## 5. 실전 매핑 — 구글 SSO, 카카오·네이버 간편로그인

"간편로그인(소셜 로그인)"의 본질은 **OAuth의 인가 절차를 빌려 인증을 수행**하는 것입니다. 제공자가 OIDC를 지원하면 ID Token 검증으로 신원을 확인하고, 지원하지 않으면 Access Token으로 프로필 API를 호출해 신원을 확인합니다.

| 제공자 | 프로토콜 | 신원 확인 방법 | 비고 |
| :--- | :--- | :--- | :--- |
| **구글 로그인** | **OIDC** (완전 준수) | ID Token 검증 | Discovery, UserInfo 등 표준 전체 지원 |
| **카카오 로그인** | OAuth 2.0 + **OIDC 옵션** | 기본은 사용자 정보 API(`/v2/user/me`), OIDC 활성화 시 ID Token | 콘솔에서 OIDC를 켜면 표준 방식 사용 가능 |
| **네이버 로그인** | OAuth 2.0 | 회원 프로필 API(`/v1/nid/me`) 호출 | OIDC 미지원 — Access Token으로 프로필 조회 |

### SSO는 프로토콜이 아니라 목표

- **SSO(Single Sign-On):** "한 번 로그인으로 여러 서비스에 접근"이라는 **사용자 경험/목표**.
- 이를 구현하는 수단이 프로토콜: 모던 웹·모바일은 **OIDC**, 엔터프라이즈 레거시는 **SAML**.
- 흔히 말하는 "구글 SSO"는 **구글을 IdP(Identity Provider)로 쓰는 OIDC 로그인**을 뜻합니다.

> **핵심:** 구글 로그인은 OIDC, 카카오는 OAuth 2.0(+OIDC 옵션), 네이버는 OAuth 2.0 + 자체 프로필 API입니다. 어느 쪽이든 백엔드가 마지막에 하는 일은 같습니다 — **검증된 신원(`sub` 또는 프로필의 고유 ID)을 자사 유저 테이블에 매핑**하는 것.
